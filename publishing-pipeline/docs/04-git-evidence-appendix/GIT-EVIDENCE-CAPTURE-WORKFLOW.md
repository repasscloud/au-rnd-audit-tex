# Git evidence capture lifecycle

## 1. Declare scope

An accountable person identifies each repository, project coverage, reporting
period, expected state and acquisition mode. Record missing, private, deleted,
shallow, partial or inaccessible history immediately; do not silently narrow the
scope.

## 2. Capture immutable facts

Use an approved export, or inspect an allow-listed local repository read-only.
Capture full hashes, parents, timestamps, author and committer identities,
subjects and digests without editing them. Capture hosted issues, requests,
builds, tests, deployments, releases or tags only from supplied exports or
existing evidence; ordinary publication never queries the network.

## 3. Register supporting artefacts

Put reports, diffs, logs, screenshots or provider exports in the controlled
evidence repository and add their stable `EV-NNNN` records to the existing
program or experiment evidence catalogue.

## 4. Add interpretations only when known

An accountable supplier may explain why a material event relates to an existing
project, uncertainty, activity, experiment or evidence item. Preserve ordinary,
failed, reverted, abandoned and outside-boundary work. If the relationship is
unknown, leave it unasserted and raise a review rather than inventing it.

## 5. Confirm identities explicitly

Record a mapping only after an accountable confirmation with basis, evidence and
review reference. Similar names or email addresses are insufficient. Disputed
mappings remain disputed; replacement mappings supersede rather than erase them.

## 6. Review changes and limitations

When a repository advances, create a fresh fact capture and update the pinned
state through the controlled source-review process. Never rewrite older facts.
Record unavailable or incomplete history with a reason and accountable review.

## 7. Publish

Validate the entire graph, render in staging, compile all seven PDFs, reject all
Tectonic warnings, inspect document 04 text and layout, and replace prior outputs
only after every gate passes. Repeating unchanged inputs and repository state
must produce substantively unchanged TeX.
